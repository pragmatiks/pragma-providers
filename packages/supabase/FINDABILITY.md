# Findability audit: supabase

Each row records how a resource type meets the Pragmatiks findability and idempotency contract; the contract, the columns and the verdict rule are in `## Findability audit` of the repository's `CLAUDE.md`. Audited 2026-11-02 against `main@8754f36`; vendor documentation read 2026-11-02 (https://supabase.com/docs/reference/api/v1-create-a-project and the Management API spec at https://api.supabase.com/api/v1-json).

| Type | Identity | `on_observe` lookup | Uniqueness | Findable from send | Conflict on create | Partial create | Rerun | Verdict | Evidence |
|---|---|---|---|---|---|---|---|---|---|
| `supabase/project` | `organization_slug`, `name` (both `ImmutableField`), `region` (`ImmutableField`), `db_pass` | `Project.find_project` → `GET /v1/projects`, filtered on organization slug and name, `GOING_DOWN` and `REMOVED` excluded; more than one match raises | unknown, so no: the spec describes `name` only as "Name of your project" (256 characters) and documents no conflict response; the create takes no idempotency key (the spec's only `Idempotency-Key` header is on migrations) | unknown: `GET /v1/projects` "Returns a list of all projects you've previously created"; its consistency is undocumented | None documented: if the name is not unique, a retry that misses its own project creates a second one, after which `find_project` raises and the row cannot settle | Create, wait healthy, apply auth settings, wait until listed `ACTIVE_HEALTHY`: `on_update(None)` waits healthy, applies the password and the auth settings, waits until listed | `on_update` reapplies password and auth settings; `on_delete` treats a missing project and 404 as deleted and waits until unlisted | gap (PRA-868) | `Project.on_create`, `Project.find_project`, `Project.on_update`; Management API spec `V1CreateProjectBody`, `POST /v1/projects`, `GET /v1/projects` |
