# Findability audit: kubernetes

Each row records how a resource type meets the Pragmatiks findability and idempotency contract; the contract, the columns and the verdict rule are in `## Findability audit` of the repository's `CLAUDE.md`. Audited 2026-11-02 against `main@8754f36`, and the observe refusal of every non-computed type 2026-11-06 against `main@bc294e3`; vendor documentation read 2026-11-02.

The resource marker is the annotation `pragma.io/resource` holding the canonical resource ID (`marker.RESOURCE_MARKER_KEY`). Every other provider spells the key `pragma_resource`; Kubernetes requires automated components that annotate end-user objects to prefix the key with a DNS subdomain (https://kubernetes.io/docs/concepts/overview/working-with-objects/annotations/#syntax-and-character-set), and the Pragmatiks prefix is `pragma.io/`, as on the platform's own `pragma.io/host-specification`, so the prefix carries `pragma` and the name is `resource`. Annotation values are unrestricted, so the value is the ID itself.

Notes:

- An object written by a provider version before the annotation carries none, so a conflicting create and `on_observe` refuse it like an object made outside Pragmatiks.
- The marker is advisory: it tells this resource's earlier create from an object made outside Pragmatiks or by another resource, but anyone who can write the object can set it, and an object left by an earlier incarnation of the same resource ID is recognized as this resource's own.
- `on_update` server-side applies with `force=True`. `create_object` creates with a POST, which records the `pragma-kubernetes` field manager with operation `Update`, and the API server keeps a manager's `Apply` and `Update` entries apart: "A _conflict_ is a special status error that occurs when an `Apply` operation tries to change a field that another manager also claims to manage" (https://kubernetes.io/docs/reference/using-api/server-side-apply/#conflicts, read 2026-11-02), and a POST followed by a server-side apply under the same field manager name conflicts on a changed field (https://github.com/kubernetes/kubernetes/issues/107417, "Server side apply conflicts with itself"; the fix there, https://github.com/kubernetes/kubernetes/pull/112905, migrates ownership in `kubectl` only). Without the force, a recovered create, or any update, whose desired object differs from what the POST wrote would fail with a 409 conflict. The docs recommend it: "It is strongly recommended for controllers to always force conflicts on objects that they own and manage" (https://kubernetes.io/docs/reference/using-api/server-side-apply/#using-server-side-apply-in-a-controller). Forcing "removes the field from all other managers' entries in `managedFields`", so a field another manager also sets is taken back on every update.
- Child resources of `qdrant/database` and `agno/runner` are these types and carry their own child resource ID, so two parents of the same name in different projects never recognize each other's objects.
