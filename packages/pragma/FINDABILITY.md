Each row records how a resource type meets the Pragmatiks findability and idempotency contract; the contract, the columns and the verdict rule are in `## Findability audit` of the repository's `CLAUDE.md`. Audited 2026-11-20 against `main@7a2d8e0`; vendor documentation read 2026-11-20.

| `pragma/file` | Project (`self.project_id`, part of the resource identity, immutable) and name. No create request: the object is `files/{organization_id}/{project_id}/{name}` in the file bucket, stored by the Pragmatiks API's upload flow, which owns that key and records the `checksum` attribute on every object it stores; `on_create` only reads it. The provider releases after that flow is deployed | `File.on_observe` → head-only `get_async` of `files/{organization_id}/{project_id}/{name}`: its size, `Content-Type`, `checksum` attribute and last-modified time, with no sidecar; `None` for a missing object | Yes: an object key names one object | sync: object read-after-write is strongly consistent, "the object is immediately available for reading and metadata operations" | None: `on_create` writes nothing and fails when no file is stored. An object at the key without the `checksum` attribute was not stored by the upload flow: `File.on_observe` raises `AlreadyExistsError`, which `on_create` and `on_update` reach through it, so the host fails a create or update already-exists and settles a delete with no provider call, leaving the object; uploading the file again replaces it, since the API counts only an object with a matching `checksum` as stored | No write | `on_update` rereads; `on_delete` deletes the object only, ignoring a missing one | holds | `File.on_observe`, `File.on_create`, `File.on_delete`; pragma-os `is_stored_content` (`services/file_upload.py`); https://docs.cloud.google.com/storage/docs/consistency, read 2026-11-20 |
