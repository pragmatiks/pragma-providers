# Findability audit: vercel

Each row records how a resource type meets the Pragmatiks findability and idempotency contract; the contract, the columns and the verdict rule are in `## Findability audit` of the repository's `CLAUDE.md`. Audited 2026-11-02 against `main@8754f36`; vendor documentation read 2026-11-02 (reference pages and https://vercel.com/openapi.json).

The deployment's `meta.pragma_resource` stamp is the resource marker, under the key every provider uses; the project and domain creates have no field that can carry it.

| Type | Identity | `on_observe` lookup | Uniqueness | Findable from send | Conflict on create | Partial create | Rerun | Verdict | Evidence |
|---|---|---|---|---|---|---|---|---|---|
| `vercel/deployment` | `project` = `project_id`, `team_id` (both `ImmutableField`); `meta.pragma_resource` = resource ID | `Deployment.find_deployment_id` → `GET /v7/deployments?projectId=…&meta-pragma_resource=…`, then keeps live entries whose `meta` names the resource; more than one raises | No: every `POST /v13/deployments` creates a new deployment; the spec has no idempotency key, and its only 409 is "The deployment project is being transferred" | unknown: the list's consistency is undocumented, the provider itself waits for the list to catch up (`wait_for_listed_deployment`), and the `meta-<key>` filter is not among the documented list parameters | None: a retry that misses its own deployment creates a second one, after which `find_deployment_id` raises on two matches and the row cannot settle | Create, wait for `READY`, wait to be listed; `on_update(None)` finds a listed deployment and waits for it | `on_update` keeps a current deployment or replaces it; `on_delete` treats 404 as deleted and waits until unlisted | gap (PRA-865) | `Deployment._trigger_deployment`, `Deployment.find_deployment_id`, `Deployment.wait_for_listed_deployment`; https://vercel.com/openapi.json (`POST /v13/deployments`, `GET /v7/deployments`) |
| `vercel/project` | `name`, `team_id` (both `ImmutableField`) | `Project.on_observe` → `GET /v9/projects/{name}` | Yes: 409 "A project with the provided name already exists." | unknown: the docs say nothing on reading a project right after its create | Raises `AlreadyExistsError` (`client.raise_for_create_status`). The create body has no tag or metadata field; the only field that could carry a marker is `environmentVariables`, which every deployment of the project would see | Create, then upsert the environment variables: `on_update(None)` patches the settings and upserts the variables | `on_update` upserts (`upsert=true`) and deletes only variables the previous configuration declared; `on_delete` treats 404 as deleted | gap (PRA-866) | `Project.on_create`, `upsert_environment_variables`, `client.raise_for_create_status`; https://vercel.com/docs/rest-api/reference/endpoints/projects/create-a-new-project (the spec now lists `POST /v11/projects`; the provider calls `/v10`) |
| `vercel/domain` | `project_id`, `domain`, `team_id` (all `ImmutableField`) | `Domain.on_observe` → `GET /v9/projects/{project_id}/domains/{domain}` | Yes: "If the domain already exists on the project, the request will fail with a 400 status code"; 409 when it is assigned to another project | unknown: undocumented | Raises: a retry meeting its own domain gets the 400, which `raise_for_create_status` reports as an HTTP error, not even `AlreadyExistsError`; the body (`name`, `gitBranch`, `customEnvironmentId`, `redirect`, `redirectStatusCode`) has no field that can carry a marker | One write | `on_update` patches redirect and branch; `on_delete` treats 404 as deleted | gap (PRA-867) | `Domain.on_create`, `client.raise_for_create_status`; https://vercel.com/docs/rest-api/reference/endpoints/projects/add-a-domain-to-a-project |
